# Host map: T3 Code

T3's injected "T3 Code orchestration" instructions own the mechanics; where they and this
map differ, they win. Tools may load late: try a tool's name once before calling it absent.

**Helpers**

| Need | T3 Code |
|---|---|
| Model ids | Tiers: models.yaml. Check them against `orchestrator_capabilities`, once per thread (`search` finds models it omits). Active families (SKILL.md section 2): a provider with a `disabled` constraint, or that doesn't offer the tier's model, is inactive. |
| Start a helper | Same provider: the native subagent tool with `model`. Another provider, a separate checkout (`isolation:"worktree"`) or background: `delegate_task` with `target.model` and effort in `target.options` (Claude: `effort`; Codex: `reasoningEffort`). With the guard hooks installed (SETUP.md), a delegation whose model is missing or not in models.yaml, or that has no effort, is denied. |
| Role → `role` | Builder → `implementation`; Planner, Strategist, Advisor, Diagnoser → `research`; Designer → `design`; QA → `test`; Reviewer → `review`. |
| Another machine | `t3_environment_links` lists linked machines; pass one's `environmentId` as `target.environmentId` (most `t3_*` tools take it too). Not linked: `t3_environment_link` with the user's words as `hint`; never ask for a pairing code in chat. |
| List existing | `t3_thread_list`, `t3_worktree_list`. Same task: `t3_thread_send` with only the new instructions (a busy thread gets it as its next turn; `t3_queue` edits it or promotes it to steer the current run). Each review or re-check is a new `delegate_task`. |
| Wake | The delegate's result arrives; follow its `next`. A thread you launched: `t3_thread_wait` only when your next step needs its result. |
| Device loop (QA helper) | `delegate_task` role `test`, passing `hostId` and device `id`; the child calls `device_open` and drives the returned `agent-device` command (`help <command>` lists options). Accessibility snapshot before screenshot; tap and the next snapshot in one shell call. |

**Tickets and PRs**

| Need | T3 Code |
|---|---|
| Tickets | `list_issues` (`query`, `state`) for the frontier, `read_issue` for body, labels, comments and linked PRs. Blockers the tracker keeps elsewhere (GitHub: `gh api repos/<owner>/<repo>/issues/<n>/dependencies/blocked_by`). |
| Working a ticket | `link_issue` the ticket to your thread; `set_issue_state` when you start and finish (`read_issue` lists the states); the closing summary goes in `comment_on_issue`. File defects with `create_issue`. |
| PR opened | `link_pull_request` right away (every stack layer). |
| CI and reviews | `watch_pull_request`, then end the turn: T3 wakes you on failed or passed checks, new comments or reviews, and conflicts. Never `gh pr checks --watch`, `sleep` or loops. `unwatch_pull_request` before handing back. |

**Worktrees and handoff**

| Need | T3 Code |
|---|---|
| Own worktree for this thread | `t3_worktree_status` first; then `t3_worktree_handoff` with a new `branch`, as the last call of the turn (`continuationPrompt` resumes there). |
| New owner | `t3_thread_launch` when the user's global instructions make rotation a standing request (SETUP.md); otherwise give the user the section 6 pointer to start it. Launch: `message` = the section 6 pointer, `title` = "<topic> (cont.)"; omit `projectId` and `modelSelection` to inherit yours. Work in a worktree: `workspaceStrategy` `{type:"existing_worktree", worktreePath}`; no project: `scratch:true`. Reply with its `link`, then stop. |
| Remove merged worktree | `git worktree remove <path>`; T3 keeps a worktree after its thread is deleted. |
| Recurring QA sweep | `schedule_task` with the sweep prompt and `schedule` `{type:"fixed_time", timeOfDay:"07:00", weekdays:[1,2,3,4,5]}`, `freshSession:true`. `list_scheduled_tasks` first: one already there gets updated by `scheduledTaskId`, not duplicated. Report the next run time. |

**From a shell** (an Orca coordinator, a script, or any agent outside T3; inside T3 prefer
the tools above)

```sh
t3 thread start <project|.> - --provider <instance> --model <id> \
  --option effort=<level>            # Codex: --option reasoningEffort=<level>
  [--worktree <base-ref> --branch <name>] [--title <t>] [--wait] [--json] < brief.md
t3 thread send <thread> - [--wait] < followup.md   # queued as the next turn; nothing interrupted
t3 thread show <thread> [--messages <n>] [--json]
t3 thread list [--project <id|path>] [--json]
```

- `--provider` is the instance id from `orchestrator_capabilities` (e.g. `claudeAgent`,
  `codex`); `--option` needs `--provider` and `--model`. Without `--model` the thread gets
  the project's default model; the guard hook denies that.
- `--wait` blocks until the run ends: exit 0 done, 1 failed, 2 waiting for an answer
  (read it with `thread show`, reply with `thread send`). Use it in a background shell call,
  never in a loop.
- `t3 environment list` shows linked machines; `t3 project add <path>` registers a repo.
